# Real-app test run: findings and decisions

The first run of the whole process on a real app (the KeyCraft demo shop), done by the user in a second pi while the findings were
collected here and **not acted on** until the run was over. This is the record: 32 findings (F1 to F32) and the decisions of the QA
grill (D-QA-1 to D-QA-11). The plans that came out of it are [PLAN_QA_CHANGE.md](PLAN_QA_CHANGE.md) (the QA redesign, the next phase)
and [ROADMAP.md](ROADMAP.md) (all remaining phases, their order and the other workstreams).

Kinds: bug, ux, idea, design, policy, cost, praise, question. Evidence names files of the test project (`projects/keycraft/...`).
"Not acted on" means exactly that: none of this is implemented yet; see the phase list in [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md#6a-phases-after-the-real-app-run-p1-p5).

F1 [ux] Project page · there is no way to start a new discovery, or to enhance (re-run / extend) an existing one, from the Project page. Expected: a button there (start discovery; if one exists, "enhance" it, e.g. with extra notes, areas or sources).
   Context when noted: discovery starts only from pi (`/demo discover`); the Project page has Brief, Sources & context, Findings and Project history groups but no action for it.

F2 [idea] Discovery output · a discovery should leave a readable result: what it found about the app, what the additional research (sources, notes, links) contributed, and the guidance it would use for the storyboard phase. Expected: one place in the panel to review and understand the gathered information (the app itself and the extra research), and what the Director will carry into the storyboard.
   Context when noted: findings exist as a list (strength, weakness, friction, value, use case, length) with evidence; no summary document and no explicit "storyboard guidance". F1 and F2 belong together (start/enhance it, then read what it produced).

F3 [ux] Live preview (Activity drawer / discovery) · the preview picture is small. Expected: expand it into a bigger popup panel; the enlarged view must still update live with the picture, not be a frozen snapshot.
   Context when noted: the drawer shows a live frame preview during discovery and recording; no way to enlarge it.

F4 [idea] Login between discovery and recording · the login (session) should be checked and refreshed between phases, not only once at the start: a session that was valid during discovery may be expired when recording starts (and could expire mid-take). Expected: before recording (and before discovery) the Director/engine checks the session is still logged in and, if not, prompts for a re-login and carries on, instead of recording a login screen.
   Context when noted: asked together with the question "when do we add authentication and session login" (answer: slice S7, not started). Today no login support exists beyond a hand-made storage file being picked up if present.

F5 [question→idea] Discovery budget on the Project page · the budget (screens / actions / minutes) is only a Config setting (global, with a per-project override). Question: should the Project page show and set it, so it can be chosen when a discovery is started or enhanced (F1), and extended when it runs out?
   Context when noted: defaults 40 screens / 150 actions / 20 minutes per discovery session; enforced in the engine; shown in the Activity drawer during discovery. Answer given in chat; the decision comes at the summary. Linked to F1 and F2.

F6 [bug+idea] Discovery progress bar stalls · the segmented progress bar during discovery suddenly stops moving. For S6 (parallel discovery): the discovery control cycle needs more attention: the Director must make sure every area gets attention, and the progress bar(s) (one per lane) keep updating.
   Context when noted: the bar is driven by what the Director declares (a plan of areas, each marked done by the Director); it is not measured by the engine. A stall most likely means an area was never marked done (or the plan was never declared / was changed). To confirm in the run: which segment was current when it stopped, and whether the Director was still working. Answer given in chat. Linked to S6 design (per-lane progress, coverage check, stall indicator).

F7 [ux] Activity drawer · it should open as a docked side panel that shares the screen with the workspace, not as an overlay on top of it. And when the drawer is hidden, the footer strip should always show the current task and its progress.
   UPDATE (user): the bottom bar already shows progress in general, so the footer part may already be covered. Only the "current task detail" (e.g. which discovery area) is unconfirmed. Keep F7 mainly as: docked side panel instead of overlay.
   Context when noted: reverses decision D101 (the drawer overlays on purpose, so the workspace does not reflow). The strip already shows a running job with a percentage ("Render 50%", "Discovery 12%") but not the current task detail (for discovery: the current area/step, e.g. "area 2 of 5 · search"); with no plan declared the discovery percentage is only the budget burn. Design points for the summary: how wide, resizable, what happens in a narrow window (fall back to an overlay below the workspace threshold), and what the footer shows per job (task name + step + bar + ETA).

F8 [praise] Recording progress · the segmented progress bar during the recording looks great and works well. Keep it; use it as the model for discovery (F6) and for the per-lane bars in S6.

F9 [ux] Director working after the recording · after the recording the agent/Director works for quite some time (analysis, then writing the voice-over). The UI should show that, and not make the user believe there is an action for them.
   Context when noted: the band and strip only know engine jobs. A Director turn is not a job, so while it works the band shows either "Needs you · <take to approve>" with a Continue button (a draft newer than the newest approved version) or "Waiting · for the Director: …" (with a tooltip saying nothing is running). Neither says "the Director is working now". By design D101-era rule: waiting for the Director is never shown as running, because the engine cannot see the Director. Design points for the summary: an "agent working" signal (the pi extension sees tool calls and turn events), shown in the band, the strip and the stepper with what it is doing ("analysing take-001", "writing voice-over v1"); and what to do with "Needs you" while the Director is busy (still true, but secondary). Related: F6, F7.

F10 [ux+idea] Recording tab: raw take playback and timestamped notes · "play raw take" shows a large player inline, so the rest of the UI is not usable while it plays. Wanted: a recording review workspace.
   Layout asked for (3 columns): LEFT ~25%: chapters (scenes) and their frames (keyframes), acting as navigation guides (click = jump). MIDDLE ~50%: the video, with the Director's comment and the goals for the current chapter shown above it; the progress bar carries marks for the individual chapters. RIGHT ~25%: notes: the list of previous notes plus a note entry/edit box for the selected note or the one about to be added.
   Notes: while the recording plays, a key (e.g. "+") creates a new note that references the current timestamp and chapter automatically; notes are editable and attached to the chapter.
   The replay window must be smaller, so the rest of the page stays usable.
   Context when noted: today the take card has "play raw take" (an inline <video controls>), a keyframe strip per scene, and "Request a new take" with one free-text note for the next take; no per-moment notes. Data that exists for this: scene spans and marks with times from the take analysis (and keyframes at marks), the storyboard's scene intent/goals/emphasis, the Director's confidence reasons. Design points for the summary: where the notes are stored and how they reach the Director (a review message like the storyboard/voice-over review, input log entries, used when requesting a new take or rewriting the voice-over); what "the Director's comment" is today (confidence reasons, findings, scene intent); keys (+ to add; Space/arrows for playback; must not clash with the map zoom keys and the ? sheet); a smaller/detachable player (docked in the middle column, not overlay); relation to F2 (readable discovery/analysis output) and F9.

F11 [ux] Approve & use does not say what happens next · after "Approve & use" the user is not told what comes next. The Director's work that follows (here: writing the next stage, e.g. the storyboard / voice-over) needs its own progress bar and a message ("The Director is now writing …"), so the user knows it is working and that they have nothing to do yet.
   Context when noted: Approve & use starts an agent turn (notifyAgent); the panel only shows a toast "… approved and in the production line" with Undo. There is no "what now" text and no progress for the Director's turn. Same root cause as F9 (a Director turn is not an engine job, so the strip/band cannot show it); F6 (discovery progress is model-declared) is the other half. Design points for the summary: (1) after Approve & use, the toast or an inline notice states the next step and who does it ("Recording is unlocked. The Director records it next." / "The Director is writing the voice-over: nothing for you to do yet."); (2) a "Director working" state with a task label and, where the stage has known parts (scenes), a segmented bar like the recording's (F8); (3) the band switches from "Needs you" to "Director working" at once. Group with F9.

F12 [bug-prevention/doctor] Environment overrides · the second pi instance was started from a previous test terminal that still had env overrides, so it ran with settings the user did not expect; a restart was needed and much time was lost. Wanted: `/demo doctor` (and ideally the panel at start) warns about every environment override in effect, naming the variable, the setting it overrides and the value from the config file it hides.
   Context when noted: env overrides exist for root, panelPort, ttsChain, voiceName, improvise.models, roles.annotationDesigner.model, brand (DEMO_REC_ROOT, _PANEL_PORT, _TTS_CHAIN, _VOICE, _IMPROVISE_MODELS, _ANNOTATION_MODEL, _BRAND) and DEMO_REC_CONFIG (a different config file); also DEMO_REC_NO_OPEN and DEMO_REC_NO_VOICE_LIST (test switches that change behaviour). Config → "From environment" shows them only if you open it. Design points for the summary: doctor check "env overrides: N" with warn status listing each; a one-line notice at /demo new / panel start when any is set; the panel header or Config shows a persistent badge; treat test-only switches (NO_OPEN, NO_VOICE_LIST) as a stronger warning because they silently disable features.

F13 [ux/principle] Every pi/Director pass must have a presence in the UI · whenever a Director/pi turn runs, the panel should show it (what it is doing and that nothing is needed from the user). Raised after the "silent" post-processing after a recording (analysis, voice-over writing), but it can happen elsewhere too. Generalizes F9 and F11.
   Context when noted: panel actions that start a Director turn (cost class "turn"): approve, brief-draft, review-submit, version-act (Approve & use), vo-direction, plus the re-record request and the designer fallback turn; turns started by the user in the chat or by the Director on its own (after a result, after a tool finishes) are not started by a panel action at all, so no panel code knows about them. Design points for the summary: derive the state from pi's own turn/tool events in the extension (not from panel actions), so every turn is covered whoever started it; show it in the band, strip and the relevant step with a label from the tool being called; a rule for new features: "no Director turn without a visible state"; test: any turn started in the chat appears in the panel.
   UPDATE (user, later): each Director task / work task must also leave an effect in all three places: the log, the progress bar and the activity frame (drawer), not only a status line. A task with no log line, no progress and no activity entry is a gap.

F14 [idea, bigger] Ask the Director to compare versions · a way to ask the Director to compare different versions of the same artifact, mostly storyboards, recordings (takes) and voice-overs: what differs, what is better or worse, and which one to continue with.
   Context when noted: today there are deterministic diffs only for storyboard versions (scene diff) and voice-over versions (word diff, "compare with vN"); recordings have no comparison at all; the Map shows lineage but not content. Design points for the summary: entry point (select two versions in the Versions list or a "Compare with…" action → "Ask the Director to compare"); two layers: the engine computes the facts (storyboard: scenes/steps added, removed, changed; take: length, errors, dead time, retries, improvise fallbacks, keyframes per scene side by side; voice-over: words, speech/footage fit, values on the page, confidence) and the Director adds judgement and a recommendation; the result is a readable comparison linked to both versions (not a new version, not an approval), stored with the project so it can be read again; cost class turn, with a visible Director state (F13); possible follow-up actions from the result (Use for next steps on the winner; carry notes to a new version). Related: F2 (readable output), F10 (notes), BRANCHING (second narration/story).

F15 [bug / policy, high] The Director approved the recording by itself · take-001 was accepted without the user pressing anything in the panel.
   Evidence (projects/keycraft/state.json history): 12:13:46 `approved-and-used` storyboard v2 (the user, in the panel); 12:16:06 `accepted` recording v1 + `take-accepted` take-001 (the pair that `acceptTake` writes; the panel's own buttons write `approved-and-used` / `approved-only`). Cause in the code: the agent tool `demo_rec_take action=accept` calls `acceptTake` and publishes `take.accepted` with `by: "agent"` (src/tools/take.ts); the demo-voiceover skill tells the Director to do it as step 2 ("demo_rec_take accept the take you are writing for"). It is the only agent-callable approval path (storyboard, voice-over, annotations and final render can only be approved from the panel).
   Why it matters: the product promise (README, GUIDE.md, TUTORIAL-101.md, panel hints) is that approving is the user's decision and the agent cannot approve; here the take shows as Approved and is on the production line, and the voice-over was written from a take the user never reviewed. It also makes F10 (recording review) moot, because the review gate was skipped.
   Design points for the summary: (a) remove the agent's accept action, or make it a proposal ("I suggest accepting take-001") that the user confirms in the panel; (b) the skill should write the voice-over from the latest take WITHOUT accepting it, or wait for the user's approval; (c) decide whether an unapproved take may be the input of a voice-over draft at all (a draft version built on an unapproved parent is a different state than today's "a version can only be approved when its parent is approved"); (d) a test that no agent tool can approve; (e) correct the docs wherever they say "the agent cannot approve" until it is true. Related: F9, F11, F13.

F16 [ux] Voice-over panel: show the scene's frames even where the script has no hit · under the narration the panel shows only the pictures for anchors the script actually uses; marks the script does not mention, and the scene's start and end frames, are hidden. Wanted: all the scene's keyframes shown (in time order), with the ones the script uses marked and the others shown as "not mentioned", so the user can see what the narration skips.
   Evidence from take-001 (analysis.json vs voice-over v2): 01-home has marks hero-cta and categories-visible, the script uses only categories-visible; 02-eliza-chat has 5 marks (chat-open, question-sent, mirror-reply, plug-request, product-plug), the script uses 3 (question-sent, mirror-reply, product-plug), so chat-open and plug-request are never shown; every scene also has a start and an end keyframe (4 to 7 frames per scene) that are not shown at all; intro, bridge and outro sections show no pictures.
   Design points for the summary: a filmstrip per section = start, every mark, end, in time order; used anchors show the phrase they pin, unused ones are labelled "not mentioned in the narration" (a prompt to either mention the moment or cut it); click a frame to insert its [@mark] at the cursor in the narration (new idea, optional); intro/outro could show the first scene's start and the last scene's end frame; same data and thumbnails as the chapter/frame navigation asked for in F10, so build once.

F17 [policy / cost, high] The Director went on by itself after "Approve & use" and spent voice credits without asking · after the voice-over was approved in the panel the Director carried on through voice synthesis, edit, a draft render and the annotation designer (twice), without the user knowing and without a cost dialog.
   Evidence (projects/keycraft): 12:19:33 vo v2 `approved-and-used` (the user's click in the panel); 12:20:19 (46 s later) vo/audio/v2.json: engine elevenlabs, billedChars 1231, totalSec 108.56; at the same time a draft render (render/v1.json, by `edit`); annotations v1 and v2 by `annotation-designer`, both based on vo v2. Phase now voice-edit.
   Cause in the code: Approve & use starts a Director turn (the button says so); the approval message tells it "Voice synthesis is unlocked (demo_rec_tts version=2)"; the agent tool `demo_rec_tts start` has no human confirmation: the cost dialog (D91/D95, "never skippable for the voice") exists only in the panel path "Generate voice & render…". `demo_rec_tts check` shows the estimate only if the agent chooses to call it. Nothing in the skills tells the Director to stop before synthesis and wait.
   Note: the storyboard v2 and vo v2 approvals were the user's clicks (`approved-and-used`); only take-001 was accepted by the agent (F15). The problem here is not an approval, it is what the Director does after one.
   Design points for the summary: (a) a hard gate in the tools: anything that spends money (TTS billed, a new take, a separate designer run) refuses unless the user confirmed it in the panel dialog or in chat in that turn (a confirmation token the engine issues, not the model's say-so); (b) the Director's skills: after an approval do ONE thing, say what is next and what it costs, then wait; (c) which steps may run on their own after an approval (the free ones: analysis, annotations proposal) and which must ask; (d) the activity of an unasked step must at least be visible (F13).
   MORE EVIDENCE (same project, later): voice-over v3 approved 13:00:57 (user click) → vo/audio/v3.json 13:01:37: ElevenLabs, 474 characters billed, 40 s later, again without a cost dialog; the sync edit then made draft render v7 (13:01:42). Annotations v4 approved 13:02:41 → final render v8 started 13:03:04 by `agent`, 23 s later. The final renders v2 (12:31:13, 63 s after annotations v3 approved), v6 and v8 were all started by the Director (`by: agent`) although the approval message says to OFFER a final render. So the Director starts finals (CPU, QA, and the next steps) without being asked, on top of the unasked voice synthesis.

F18 [ux / interaction] Confirm in either place and keep both in sync · when the Director needs the user to decide something it should ask in the UI and in the chat and wait for either a verbal answer in the chat or a click in the panel. A confirmation given in the chat must update the UI (same state as a click); a click must reach the chat/Director.
   Context when noted: today the UI is the only place that can approve (and the agent's take accept, F15); clicks reach the Director as quiet notes or as a started turn; a chat confirmation has no way to change the project's state, so the panel could never reflect it. Design points for the summary: a "pending question" object owned by the engine (id, what, options, cost) shown in the band and as a dialog in the panel and as a chat message; answering either way resolves it once and the other place updates; the Director waits on it (a tool that blocks / returns when answered); relates to F15 (approvals), F17 (cost gate), F9/F11/F13 (visible state).

F21 [question→idea] Zoom limit "at most 2 zooms per demo" is not configurable · where is it configured, and it should rather be zooms per minute and zooms per scene, with a way to override.
   Answer/evidence: it is a hard-coded constant `MAX_ZOOMS = 2` (src/annotations/types.ts), together with `MAX_ZOOM_FACTOR = 1.8` and `MAX_TEXT = 60`. It is not in Config or on the Project page. It is enforced in five places: (1) file validation of an annotation version (`file.ts`: a version with more is rejected), (2) the designer's own selection that pre-enables the best half (`design.ts`, twice), (3) the panel's edit rules (`draft.ts`: "at most 2 zooms per demo — turn another zoom off first", for both enabling and a re-target), (4) the input pack text the designer reads ("Caps: ≤ 2 zooms per demo"), (5) the skill and docs text (demo-annotations SKILL, ANNOTATIONS.md). A fixed 2 means a 6-minute demo gets as many zooms as a 1-minute one, and a 1-scene demo can use both on one scene.
   Design points for the summary: new settings under Config → Annotations (which has only autoSuggest today), with the usual layers (global, project override, Scopes): zooms per minute (e.g. 1.0), zooms per scene (e.g. 1), and an optional absolute cap per demo; the effective cap for a demo = min(ceil(minutes × per minute), scenes × per scene) unless the absolute override is set; the same effective cap must feed all five places (one function, not five constants), and the input pack tells the designer the real number; a per-demo override in the Annotations tab ("allow N zooms for this demo", with the reason it is limited: zoom is the loudest item, noise 1.5, and the most expensive to render) saved on the annotation version, not global; show the cap and the use ("2 of 3 zooms") in the budget meter. Also consider the other hard caps (factor 1.8, text 60 chars, one callout at a time, spotlight only at value 5) as settings later. Related: F19/F20 (Annotations tab), the budget meter.

F22 [ux] Silent cheap steps need a notification (render, and in general) · some steps are fine to run on their own because they are cheap (e.g. an edit and draft render after the voice, a cheap re-render, analysis, the annotation proposal), but the user still needs to be told that they ran: a notification (what ran, result, where to look), not a silent change.
   Context when noted: raised on render, where drafts appear in Render without an announcement (a "new" badge on the step exists for results, but a draft render made as a side effect of the voice step gave no message). Principle to sort the steps: ASK first (costs money or a long time: TTS, new take, separate designer run), RUN AND TELL (cheap, automatic: edit, draft render, analysis, annotation proposal, QA re-run), NEVER SILENT. Design points for the summary: one notification mechanism for "run and tell" steps: toast + Activity entry + log line + the step's "new" badge, with what ran and a link to the result; which steps are in which class (a list in the code, with a test that no engine job or Director task finishes without a notification); relation to F13 (every pass has a presence), F17 (cost gate: the ask-first list), F9/F11 (Director working state).

F23 [ux/idea] Role label in the pi chat · in the pi chat the role that is currently speaking or asking should be visible (Director, Cutter, Voice writer, Operator, …) as a label once, in front of its text block.
   Context when noted: the cast (ACTORS.md) is a design concept: the model roles (Director, Researcher, Storyboard writer, Operator, Voice writer, Annotation designer, Brand designer) are personas of the same session model, played through skills; Cutter and QA reviewer are engine roles with no model; so today the chat shows one undifferentiated voice. Messages sent by the extension already carry a source prefix ([demo-panel], [demo-recording]) but not a role. Design points for the summary: (1) for messages the extension sends (job results, panel messages, doctor, QA, edit sync results): prefix with the role, e.g. "Cutter ·" for the sync edit result, "QA reviewer ·" for QA, easy and deterministic; (2) for the model's own text: a rule in each skill ("start each block with your role label once") and a check in review, which depends on the model obeying; a rendering-level label would need pi support (a message renderer or an assistant-text hook) that has not been checked; (3) the same role names in the panel (Activity entries, the Director-working state from F9/F13) so chat and panel agree; (4) a role is also useful in "who is asking you" (F18: a pending question shows which role asks).

F24 [question→design gap] Where do accepted QA fixes live, and does the next render keep them? · if the user accepts some fixes after a render, would that create a new voice-over or annotation layer, or be saved some other way, so that a new render does not suffer from the same issue?
   Answer/evidence (src/qa/overrides.ts, run.ts `fixRequest`, docs/QA.md): an applied fix is NOT a new voice-over or annotation version. It is a **render override** (`render/vN.overrides.json`): a shift of one narration segment by Δ ms on a COPY of the edit's timeline, for that render only; the approved script, audio and annotations stay untouched. "Apply fixes" makes a new final render that carries its source render's overrides plus the new ones (shifts of the same segment add up). Content problems (a wrong number, an error toast) are never fixed automatically. "Confirm & export anyway" is stored on that render's own QA report only.
   The gap: a normal "New render…" (from the Render screen) does not carry any overrides (the form has no "based on render vN"), and the overrides are keyed to the timeline of that voice-over's edit, so a new render, a new voice-over version or a new sync edit starts again from the unfixed timeline and the same QA item comes back; a confirmation does not carry over either. The user's expectation (fixed once = stays fixed) is only true along the chain of "Apply fixes" renders.
   Design points for the summary: make the fixes belong to the edit (a new timeline version "edit vN+1 with these shifts", visible and listed) or to the voice-over version (a "timing adjustments" layer saved with it), so every later render of that voice-over starts from them; show the fixes in effect on the Render screen and in New render ("includes 2 timing fixes from render v8: Reset"); carry confirmations forward only when the item is identical (same check, scene, anchor) and say so; decide what happens to the fixes when the voice-over or the take changes (drop them, with a message); relation to F2/F14 (versions of an artifact) and the "Never silent" rule (F22).

F25 [bug/design, high] QA "move earlier / move later" fixes do not really fix the findings · the QA proposes fixes ("move it 0.52 s earlier/later"), but after applying them the same items seem to remain. Needs a detailed look at the QA check itself (measurement, the fix, the re-check), not only the UI.
   Plan agreed with the user: discuss the QA checks in detail in a FEATURE BRANCH after this test run, before the UI fixes, then turn it into an implementation plan.
   Points to examine in that discussion: (1) is the measured drift right (Whisper on the rendered mix vs the event time; onset snapping; the 3 s search window; first-words match); (2) is the shift right (the sign and size; only the audio piece moves, but the picture around it may have been retimed by the sync edit; "no room to move" cases; pushing later segments; held frame at scene end); (3) is the re-check comparing the same thing (the new render's QA runs on the shifted audio: does `an.drift` get recomputed, does the check tolerate the 150 ms warning band, does a fix that moves by the full drift overshoot because the edit already compensated); (4) fixes accumulate across renders (shifts of the same segment add up) and may oscillate; (5) a blocked or skipped fix is not told to the user ("no room to move it" appears only inside the render); (6) values-shown-later fixes shift the voice by shown-said+300 ms, which may move the phrase away from its anchor and create a drift finding.
F26 [design, high] Fixes as an overlay on the base voice-over and annotation versions · fixes should be stored as an overlay on top of the base annotation and voice-over version used for the render, so they are tracked, listed and re-applied by later renders (this is the answer to F24, stated as the wanted design). To be discussed in the same feature branch, then written as an implementation plan.
F27 [ux, small] Accept all / accept selected blocking findings · a button to accept ALL blocking findings and one to accept the SELECTED ones (both needed), so the user can force a video through when needed (Confirm & export anyway for many at once, with the reason). A UI tweak, to do with the other UI fixes.
