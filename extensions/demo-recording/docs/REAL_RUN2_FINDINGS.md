# Real-app run 2: findings and ideas (collected, not acted on)

The ideas and findings of the second real-app run ([RUN2-101.md](RUN2-101.md)), collected here the way run 1's were
([REAL_RUN_FINDINGS.md](REAL_RUN_FINDINGS.md)): **nothing here is acted on until the user says the collecting is over**, and then the items are
grouped into phases with the user. Items are numbered R2-1, R2-2, ... in the order they were given. Ideas raised while preparing the run, before it
started, are marked "before the run".

Kinds: bug, ux, idea, design, policy, cost, praise, question. Evidence names files of the run
(`~/DemoRecordings-run2/projects/keycraft/...`) once there are any. "Not acted on" means exactly that.

R2-1 [ux, idea] Config · one change summary at the END of editing, not one confirmation per setting. Wanted: edit several settings, then see a single summary of everything that changed (a combined diff per file/scope) and confirm once, instead of the diff dialog after every single edit.
   Context when noted: raised before the run. Today every setting has its own "Review change…" that opens the diff dialog and saves that one setting (`POST /api/config-set` with `confirm: true`, per key; `src/panel/public/config.js`, the SettingRow editor), so changing four settings is four dialogs. The diff step itself is deliberate (UX9a, D125: "editing … still ends in the diff confirmation", so a result of the search can never edit the wrong layer), so the idea keeps the review but moves it to the end.
   Assessment (not decided): the review's purpose (see exactly what changes and where, never edit the wrong layer) survives if the pending edits are staged and shown together; points to settle: where staged edits live while you search or leave the screen (kept, or asked about); a visible "N changes not saved" count and a Discard; whether an env-shadowed setting ("this change has no effect right now") and a failing validation are shown per line in the summary; one atomic write per file; the keyboard path; what "Reset to default" and "Remove override" do (they are edits too).

R2-2 [ux] Config · edit the project scope directly. Wanted: when a project is open, edit that setting's project value straight from the row, without first opening **Scopes** (the layers disclosure) and choosing "Override for this project" / "Edit project". Read as: in the collapsed row ("scopes collect[ed]" in the note; to confirm with the user), the project layer should be directly editable.
   Context when noted: raised before the run. Today the row shows only the effective value and its source; the project override, the global value and the default are one disclosure away (Scopes), each with its own action (D125); there is deliberately no page-level Global / Project switch. Relates to R2-1: editing several project-scope values in a row and reviewing them once at the end is the natural pair.
   Assessment (not decided): D125 removed the page-level switch so that a search result could never edit the wrong layer; a direct project edit must keep that guarantee (the editor says "Editing the project override (keycraft)" and where it saves) and must say what it does to the global value (nothing). Points to settle: which layer a plain click on the value edits when a project is open (project, with a clear label) and when none is open (global); a way to reach the global layer that is not hidden; the "Changed" / "Overridden here" filters stay as they are.

R2-3 [idea, ux] An "Advanced" button on most stages to ask the Director to compare two versions and tell the honest difference · on the stage screens (which ones: the Director decides, see below) an **Advanced** control with "Compare two versions…": pick two versions of the stage, and the Director says what actually differs and whether the newer one is better, worse or just different, without flattery.
   Context when noted: raised before the run. This is run 1's **F14** (planned as **L6 Compare versions** in P5, size L: "select two versions → engine facts + the Director's judgement as a readable note linked to both") with two additions: the entry point is an **Advanced** menu on the stage screens, and the answer must be **honest** (say plainly when the newer version is worse, when a change was not an improvement, when nothing meaningful changed). Today there are deterministic comparisons only for storyboards (the scene diff) and voice-overs (word diff, "compare with vN", the compare table); recordings, annotations and renders have none; the Map shows lineage, not content.
   Assessment (not decided): keep F14's two layers, the engine computes the facts and the Director adds the judgement, and add the honesty rule as an instruction to the Director plus a check that it states a verdict and names the evidence (a number, a scene, a section), so "honest" is not only a tone. Stages where it makes sense, by what there is to compare: storyboard (scenes, steps, targets, length), recording (length, errors, dead time, retries, improvise fallbacks, keyframes per scene side by side), voice-over (words, speech against footage, numbers on the page, confidence), annotations (items on or off, zooms, redactions, cap), render (length, QA findings, files); not discovery or the brief for now. It is a visible Director turn the user asked for, so it costs model tokens only, needs no Allow (nothing is spent on voice or recording), and appears as a Director task in the band and Activity (P1a A2). The answer is a note linked to both versions, kept in the project, that can feed the existing fix-loop window ("ask the Director to fix the differences"). Relates to D-QA-11, the advisory coherence review (on request, never blocking, never automatic).

R2-4 [ux, idea] Recording tab · see and preview the chapters, with the snapshots as navigation hints; a smaller preview; the scene's goals and findings shown beside it · yes, you should be able to: the chapters (scenes) with their snapshot frames as the way to move through the take, the video player much smaller, and for the chapter you are on its goal and its findings.
   Context when noted: raised before the run. This **confirms run 1's F10** (planned as **R0 shared chapter/frame component** and **R1 recording review workspace** in P2: chapters and frames on the left as navigation, a smaller player in the middle with the Director's comment and the chapter's goals above it and chapter marks on the progress bar, timestamped notes on the right). Today: "play raw take" opens a large inline player that takes over the page, and below it the keyframes are a plain grid with ONE frame per scene (title, duration), not clickable and not linked to the player.
   New in this note (not in F10): the **findings of the scene** next to its goal, not only the goal. Read as two things, to confirm: (a) the discovery findings the storyboard scene is meant to show (`findings:` on the scene, the USE ones first), and (b) what the take itself found in that scene (error toast, console error, resume or retry, improvise fallback, dead time, long wait), which the take analysis already holds per scene.
   Assessment (not decided): the snapshots work as navigation only if a click seeks the player to that chapter (and the start, each mark and the end of the scene are frames, F16's "used / not mentioned" idea reused here: a mark the narration does not use is shown as such); the smaller player must stay in view while the list scrolls (the same pinned-preview behaviour as the Render screen, P1c); goal and findings above the player make the recording review a place to check the take against what the scene was for. Also feeds R2-3 (compare two takes: keyframes per scene side by side). Nothing here needs new engine data; the frames, marks, goals and per-scene findings exist.
