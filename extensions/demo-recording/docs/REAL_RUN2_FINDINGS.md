# Real-app run 2: findings and ideas (collected, not acted on)

The ideas and findings of the second real-app run ([RUN2-101.md](RUN2-101.md)), collected here the way run 1's were
([REAL_RUN_FINDINGS.md](REAL_RUN_FINDINGS.md)): **nothing here is acted on until the user says the collecting is over**, and then the items are
grouped into phases with the user. Items are numbered R2-1, R2-2, ... in the order they were given. Ideas raised while preparing the run, before it
started, are marked "before the run".

Kinds: bug, ux, idea, design, policy, cost, praise, question. Evidence names files of the run
(`~/DemoRecordings-run2/projects/keycraft/...`) once there are any. "Not acted on" means exactly that.

R2-1 [ux, idea] Config · one change summary at the END of editing, not one confirmation per setting. Wanted: edit several settings, then see a single summary of everything that changed (a combined diff per file/scope) and confirm once, instead of the diff dialog after every single edit.
   Context when noted: raised before the run. Today every setting has its own "Review change…" that opens the diff dialog and saves that one setting (`POST /api/config-set` with `confirm: true`, per key; `src/panel/public/config.js`, the SettingRow editor), so changing four settings is four dialogs. The diff step itself is deliberate (UX9a, D125: "editing … still ends in the diff confirmation", so a result of the search can never edit the wrong layer), so the idea keeps the review but moves it to the end.
   Assessment (not decided): the review's purpose (see exactly what changes and where, never edit the wrong layer) survives if the pending edits are staged and shown together; points to settle: where staged edits live while you search or leave the screen (kept, or asked about); a visible "N changes not saved" count and a Discard; whether an env-shadowed setting ("this change has no effect right now") and a failing validation are shown per line in the summary; one atomic write per file; the keyboard path; what "Reset to default" and "Remove override" do (they are edits too).

Points to settle: which layer a plain click on the value edits when a project is open (project, with a clear label) and when none is open (global); a way to reach the global layer that is not hidden; the "Changed" / "Overridden here" filters stay as they are.

   Context when noted: raised before the run. This is run 1's **F14** (planned as **L6 Compare versions** in P5, size L: "select two versions → engine facts + the Director's judgement as a readable note linked to both") with two additions: the entry point is an **Advanced** menu on the stage screens, and the answer must be **honest** (say plainly when the newer version is worse, when a change was not an improvement, when nothing meaningful changed). Today there are deterministic comparisons only for storyboards (the scene diff) and voice-overs (word diff, "compare with vN", the compare table); recordings, annotations and renders have none; the Map shows lineage, not content.
   Assessment (not decided): keep F14's two layers, the engine computes the facts and the Director adds the judgement, and add the honesty rule as an instruction to the Director plus a check that it states a verdict and names the evidence (a number, a scene, a section), so "honest" is not only a tone. Stages where it makes sense, by what there is to compare: storyboard (scenes, steps, targets, length), recording (length, errors, dead time, retries, improvise fallbacks, keyframes per scene side by side), voice-over (words, speech against footage, numbers on the page, confidence), annotations (items on or off, zooms, redactions, cap), render (length, QA findings, files); not discovery or the brief for now. It is a visible Director turn the user asked for, so it costs model tokens only, needs no Allow (nothing is spent on voice or recording), and appears as a Director task in the band and Activity (P1a A2). The answer is a note linked to both versions, kept in the project, that can feed the existing fix-loop window ("ask the Director to fix the differences"). Relates to D-QA-11, the advisory coherence review (on request, never blocking, never automatic).

R2-7 [question, ux, policy] (**addressed by work package 2c**, D-R2-3: the step stays, the button says it) After the voice is recorded the Director starts a DRAFT RENDER, though the annotation step has not happened · why does it, and should it?
   Answer (checked in the code): by design. "Generate voice & render" (the panel) runs the voice (behind the Allow), then `startEdit` (the audio-led edit, which writes the timeline), then a draft render of that edit, all as engine jobs without a Director turn (`src/panel/voice-routes.ts`, the `afterDone` of the voice job); on the Director's side the voice-over skill's step 3 does the same with `demo_rec_edit start`. The **edit is required**: annotations are placed on its timeline, so the annotation step cannot start without it. The **draft render is not required**: it is a 960×540 video tagged DRAFT with "no annotations", made so you can watch whether the narration lands on the footage before annotating (D11, audio-led and event-anchored); a draft can never be approved. It costs no model and no voice, only local ffmpeg time. The step that really follows is also automatic: the annotation designer starts by itself after each edit (`annotations.autoSuggest`, on by default; an announced Director turn).
   Context when noted: raised before the run, from the user's first-run experience: the sequence feels like "voice, then render" with no say in it, and the mental model is voice, annotations, render. Run 1's F22 already asked that cheap automatic steps are told (run-and-tell): this one is told (a "new" badge and an Activity line) but not chosen. Today the only related setting is `render.keepDrafts` (how many draft renders keep their video files; older ones keep the record only).
   Assessment (not decided): the edit's stats (sync per scene, narrator waits, off-sync, drift) are available without a render, so what the draft adds is only watching. Options: (a) a setting, e.g. `render.draftAfterVoice` (on / off), off meaning the voice step ends with the edit and its numbers, and "Watch a draft" is a button in Render or on the Voice screen (one click, local, no cost); (b) keep it automatic but say so on the button ("Generate voice & render: the voice, the edit and a draft to watch"), which the button's wording today only half says; (c) leave as is. The deciding question is whether you usually want to watch the sync before annotating (then (b) is enough) or go straight on (then (a)). Relates to R2-5/R2-6 only by place (the same screens) and to the thin early checks (P1d): a sync check without a render is possible from the edit's numbers.

R2-8 [bug, high] (**addressed by work package 2a**, D-R2-4) A configured brand that does not exist makes the edit job fail, though the edit itself worked · the draft render after the voice tried to use the `datadog-poc` brand, which does not exist in the run's folder; the job failed and the step to the annotations did not come. Wanted (as the user put it): keep the cheap draft step, but the render only chooses a brand that exists and falls back to the default when needed.
   Where the brand is decided (checked in the code): `config.brand`, the effective setting `brand` (built-in default `neutral`; your global `~/.config/demo-recording/config.json` and the project's own `config.json` can set it, here `datadog-poc` in both the global file and run 1's `projects/keycraft/config.json`; the env override is `DEMO_REC_BRAND`). `startEdit` (`src/tools/edit.ts`) writes the edit first (`buildEdit`: the timeline `edit/timeline.vN.json`), then calls `runRender` with a draft request without a brand, so `planRender` takes `[config.brand]` and `resolveBrand(root, "datadog-poc")` throws `unknown brand "datadog-poc" (available: neutral)`. Brands are looked up in `<root>/brands/` plus the built-in `neutral`; a new working folder (`DEMO_REC_ROOT=...`) has no `brands/`, while the global config still names the old brand.
   What it does (the damage): the whole edit job fails, so there is no `edit.finished` success report, the sync stats are not shown, and the automatic hand-off ("Next: Annotations", `annotations.autoSuggest`) is skipped, although the timeline was written and the annotations only need that. A missing brand costs the user the next step, not just the draft.
   Assessment (not decided): (1) the default brand is resolved with a fallback: when the configured brand is not found, use the built-in `neutral`, and SAY so (a warning on the edit report and the render's warnings, a line in Activity: "brand datadog-poc not found under <root>/brands, rendered with neutral"); an explicitly chosen brand (the user picks one in New render, or the Director passes one) still fails with the clear message, because choosing is not guessing. (2) A draft render failure after a successful edit is a warning, not a failed edit: the edit result (timeline, sync stats, the annotation hand-off) is reported either way, and the draft can be re-run (`demo_rec_edit rerender`, or a button). (3) `/demo doctor` and the Config screen warn when the configured default brand does not exist under the current root ("a new root has no brands: copy them or pick one"), the same family as the environment-override warning (A6). (4) Where `/demo brand use <name>` sets a brand, say which root it was found in. Test: a root without the configured brand, "Generate voice & render" ends with the edit report, a draft rendered with neutral and the warning, and the annotation hand-off; an explicit unknown brand still fails fast.
   Immediate workaround for run 2 (added to RUN2-101.md step 1): copy the brands (`cp -R ~/DemoRecordings/brands ~/DemoRecordings-run2/brands`) or run `/demo brand use neutral` in the run's pi before the voice step. If it already failed: the timeline exists; fix the brand, then ask the Director to re-render the draft and to continue with the annotations.

Test on the real data above (and a seeded 40-row list): no element of the list reaches past the list's right edge at 1400 and 900 px, the list is 10 % wider, the pin holds while scrolling and is released at the end.

R2-12 [ux, design, reverses a decision] The Activity drawer should be docked (a slide-out that pushes the control room narrower), not an overlay · when opened, the drawer should not cover any element of the control room; the UI should shrink in width and sit beside it.
   Context when noted: raised before the run; the user remembered it as already done, but what was decided and built is the OPPOSITE: **D101** (UX grill, 2026-10-15) and the Activity contract in UX.md: "The drawer overlays the workspace, never squeezes it, and opens only on user request" (reason given: reclaim the idle width of the old always-on Live column without hiding work or errors; the workspace keeps its width for the list + inspector layouts, tested at 1400 and 900 px). Today (`ds/components.css`): the strip is `position: fixed` along the bottom (one line, full width); the drawer is `position: fixed` on the right, between the header and the strip, `inline-size: min(30rem, 100vw)`, `z-index: var(--layer-drawer)`, with a shadow, so it covers whatever is under it; it is non-modal (the page behind stays usable), takes the focus, gives it back, closes on Escape and never opens by itself (also closed again after a reload).
   Assessment (not decided; this supersedes D101 if accepted): docking is a fair change of mind, with consequences to settle. (1) **The layouts are container-query based**: the Render grid goes two-column only above 72rem (1152 px) of its container, the list + inspector screens hide their list below 52rem. With a 30rem (480 px) drawer docked at a 1400 px window the workspace is about 920 px, so the Render screen would drop to ONE column (and lose the pinned two-fifths preview) and the Voice over / Annotations / Storyboard lists would sit near their narrow breakpoint, exactly while you watch Activity. Options: a narrower drawer (about 22 to 24rem), lower breakpoints for the docked case, or accept the single column while it is open; the choice should be made by trying it on real data (the run-1 project) at 1400 px. (2) **What shrinks: DECIDED by the user: the main content only.** The header (with the stepper) and its next-action band keep the full width, and so does the bottom strip; only the area between them shares its row with the drawer. A simpler case than shrinking everything: the measured header height (`--hwrap-h`) and the pinned panels' offsets do not change, and the drawer's vertical extent stays "between the header and the strip" as today. (3) **Small windows keep the overlay**: when the window minus the drawer is below the narrow breakpoint there is nothing left to squeeze, so the drawer falls back to today's overlay (automatically, by width). (4) Keep: never opens by itself, Escape closes, focus in and back, the strip stays, the drawer works with the keyboard. Optional: remember docked and open across a reload (today it is closed after a reload on purpose), and a draggable width. Test: at 1400 and 900 px with the drawer open and closed, on the real project, nothing is covered, nothing is cut, every screen still usable; at 900 px it overlays.
   Second question in the same note (answered in chat): how the activity is shown on a phone or a very small device. Answer: the panel was never designed for it (the narrowest layout designed and tested is 900 px; below it the drawer, `min(30rem, 100vw)`, is a full-width panel between the header and the strip). **Decided by the user: no phone or small-device use is needed**, so nothing is designed or tested below 900 px, and point (3) below only keeps the overlay as the safe fallback for a window too narrow to squeeze, not as a supported small-screen mode.
   Decided so far (user): docked and squeezing the main content only; header, band and strip stay full width; no phone use. Still open: the drawer's width and what happens to the Render two-column layout while it is open (point 1), and whether it is remembered across a reload.
